# bh-029 monster model brief (Builders M1–M6)

You build enemy models for the Godot 4.7 game Beyond Heroes (`A:\Python\beyond-heroes`) for its new island, **Zarael** —
read `work/lemondev/bh-029/contract.md` first (story, theme, the roster table, house rules). Everything is generated by
Python run in Blender 5.2 — no third-party meshes, deterministic, no manual edits. The Orchestrator writes the gameplay
(stats, attacks, AI, spawning); you deliver models that satisfy this contract.

## Theme
Zarael is ancient, stepped stone in the spirit of Mesoamerica — **visual only, no real-culture names**: feather crests and
capes, quilted cotton armour, obsidian-edged clubs and blades, jade and turquoise mosaic, carved stone constructs —
crossed with the **Wirewrights' ancient engineering**: glowing gold/copper wire inlaid in channels and coiled round
limbs and staves. The island is **corrupted**. **GLOW COLOUR RULE (user request, 2 Oct 2026): every glow on every Zarael model is PURE WHITE** — `BH_Emissive` (and `BH_WeakPoint` where used) albedo (1.0, 1.0, 1.0), emission (1.0, 1.0, 1.0); no violet-red, magenta, gold, teal, green-gold or orange tints on wire, runes, eyes, coils or cores. Corruption reads through the *form* (cracks, chains, wire grown through flesh, broken stone), not through colour. Keep emission energy moderate (≈4–6) so white does not bloom the silhouette away. The only exception: real fire (a furnace mouth, a burning censer's coals) may use `BH_Coals`-style orange, but any wire/seam/glyph glow on those models is still white. The **Kharvenn** chain-priests (enemies 8, 9, 15, 18) are foreigners: grey iron, black cloth, rune-chains with white-glowing runes — not Zarael stone. Monsters level 30–53: they should look dangerous and well made. The gameplay camera is high
(≈50–55° pitch at 16–26 m): silhouettes and glow must read at that distance.

## Humanoid contract
- Module `tools/blender/characters/enemy_<id>.py` exposing what the others expose (`SCALE`, `PROPS`, `PALETTE`,
  `PALETTE_COLORS`, `CLIPS`, `build(body)`, optional `finish_mesh`). Build one character:
  `cd tools/blender/characters && "<blender>" -b --factory-startup --python build.py -- <id>` → writes
  `game/assets/characters/<id>.glb`. Copy an existing enemy's `<id>.glb.import` next to it (same settings, e.g.
  `nodes/use_name_suffixes=false`), changing only paths, and delete the `uid=` line (Godot assigns one). The model bakes
  the shared enemy base clips + your `CLIPS`. Choose `CLIPS` from the shared library to suit the role (look at what
  comparable enemies list): melee sets (`axe_*`, `sword_*`, `spear_*`, `mace_*`, `dual_*`, `shield_*`), casting
  (`cast_quick`, `cast_weapon`, `cast_heavy`, `cast_area`, `staff_*`), ranged (`throw_*`, `bow_*`/crossbow as available),
  and for bosses the `boss_*` set (`boss_slam`, `boss_charge`, `boss_roar`, `boss_summon`, `cast_ultimate`, …). Report the
  exact list.
- Weapons are rigid on `weapon.R` / `weapon.L` (see `K.add_weapon`), shields face −Y.
- Budget: regular monsters ≤ 20k triangles, bosses ≤ 35k. Author at the natural height: regular ≈ 1.8–2.0 m, big
  brutes ≈ 2.6–3.0 m, bosses 3–4.5 m (the game also scales).
- Materials: contract names `BH_*` with a per-character palette (`PALETTE_COLORS`) exactly as the existing enemies do.
  `BH_Emissive` for glows (eyes, wire, runes, molten seams), `BH_WeakPoint` for a glowing core if your spec asks.

## Creature contract (quadruped / 8-leg / floating)
- Script `tools/blender/creatures/build_<id>.py`, runnable like the existing ones, writing `game/assets/characters/<id>.glb`.
- Do NOT edit existing scripts. Import from them, or copy code into your own module if a function needs changes.
- Clip names: the generic set (`idle, idle_look, walk, run, run_combat, hit_light, hit_heavy, stagger_small, knockback,
  death, death_back, alert`) plus your attack clips, which MUST be prefixed with your stem from the contract (e.g.
  `cat_pounce`, `cat_swipe`, `scorp_sting`). Clips in place, 30 fps.
- `game/assets/characters/creature_meta.json`: merge ONLY your own prefixed clip keys (length, loop, hits = seconds where
  the blow lands). Re-read the file immediately before writing, keep every other key untouched, write, re-read and
  verify. Other builders merge into the same file concurrently.
- Floating models follow the wisp convention exactly: static node hierarchy, no armature, origin = creature centre,
  child nodes named `core`, `ring_1`, `ring_2`, `ring_3` (each ring tilted by its own transform and spun by the game
  about its local up axis), and `ribbons`. The game hovers it ~1.2 m above ground and animates everything.

## Validation and evidence (per model)
- An import check on a scratch project (copy your GLBs + `.import` into `work/lemondev/bh-029/scratch/m<n>/proj/` with a
  minimal `project.godot`, run Godot `--headless --path <that> --import`, then a tiny script listing each AnimationPlayer's
  clips and loop modes), or `godot_check.py --scratch <dir>` if it fits — never touch shared evidence files.
- Workbench previews: `preview_enemy.py` (`--iso` for the gameplay camera, `--clips` for poses). Look at them.
- Evidence dir `work/lemondev/bh-029/evidence/models_m<n>/`: `<id>.md` (module, GLB, triangles, materials, height, clips,
  palette, what makes it distinct, build log excerpt, known limitations), `<id>_rest_iso.png`, `<id>_clips.png`.
- Up to 3 revision passes per model on your own previews. Prioritise: correct rig/clips, readable unique silhouette,
  clean deformation, then detail.

## Rules
- Write ONLY: your modules, your GLBs + `.import` files, your keys in `creature_meta.json`, your evidence dir, and
  scratch files under `work/lemondev/bh-029/scratch/m<n>/`.
- Never run `build.py -- all`, `-- meta`, or anything that rewrites other characters, `anim_meta.json` or weapons.
- Never run Godot on `game/` (no `--import`, no editor). Never kill Godot/Blender by image name — only your own PIDs.
- No Filipino words, names or folklore; no real-culture names.
- Final message: a concise report — per model: id, files, triangles, height, clips (with prefixed creature clip names
  and hit times), materials/palette notes, and known limitations. Plus anything the Orchestrator must know to wire
  the model (scales, sockets, which clip is which attack).
